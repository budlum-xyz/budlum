## 2. How these numbers were obtained without a Rust toolchain for the workspace

The workspace does not build in this environment (no crate registry reachable, so no
`cargo check`). The gates themselves do not need the workspace: each gate module is
standard library only, and two of them borrow one helper. So the gate's own source
was compiled as a standalone binary and pointed at the repository:

```sh
mkdir -p /tmp/gates && cd /tmp/gates
cp <repo>/xtask/gates/src/gates/indexing_is_not_new.rs .
# plus the strip_test_mods helper and the functions it needs, copied verbatim from
# capability_modules_are_wired.rs, so the scan is the gate's scan and not a rewrite
cat > main.rs <<'RS'
mod capability_modules_are_wired;
mod indexing_is_not_new;
fn main() {
    match indexing_is_not_new::run(std::path::Path::new(".")) {
        Ok(m) => println!("OK {m}"),
        Err(m) => println!("ERR\n{m}"),
    }
}
RS
rustc --edition 2021 -O main.rs -o gatecheck
cd <repo> && /tmp/gates/gatecheck
```

The same shape runs `guards_reachable`, `dead_pub_api` and `no_idle_code` from one
binary (the first two need a two-line stub for the self-test's scratch directory).
Two independent checks that the harness is faithful rather than a lookalike:

1. `indexing_is_not_new::self_test()` passes inside the same binary.
2. The numbers reproduce the CI annotation exactly: `182 | baseline: 173` and
   `unwired guards: 5 | baseline: 3`.

A number that did not reproduce is worth recording: `no_idle_code` reports 116 newly
idle public items under this harness while the CI Gates job does not list it as red,
so the harness is *not* faithful for that gate and its output is not used here. That
difference is a question for the gate, not a finding about the tree.

## 4. Why the remaining two are not fixed here

Every file the two gates name is inside a path an open pull request has locked:

| Path | Open pull requests that change it |
|---|---|
| `src/storage/bud3/limits.rs` | #45, #57 |
| `src/storage/bud3/placement.rs` | #45 |
| `src/storage/bud3/registry.rs` | #8, #9, #45, #55, #59, #65 |
| `src/storage/bud3/segment.rs` | #43 |
| `src/storage/bud3/content_id.rs` | #8 (the branch on the other root) |
| `src/core/block.rs` | #9 (the branch on the other root) |

Section 15.3 item 3 of the directive says one owner per lock path, and a second
branch editing a locked path produces the collision PR #72 measured 332 times. So
the decision below belongs to the owning package, and each one is a decision, not a
sweep:

1. `admit_lifetime` and `admit_mobile_quota` need a caller. The admission rules exist
   and are tested; `StorageTxV3::RenewObject` exists in `src/storage/bud3/tx.rs`, and
   the renewal entry in `registry.rs` is where a lifetime check belongs. Either the
   object-lifecycle package wires them there, or the module declares
   `WIRING: unwired` with the package that will. Both close the gate; only the first
   closes the hole the functions were written for.
2. The same question, one level up, for the other eight names: a placement share that
   no placement code reads is a number in a struct, and `total_source_symbols` is a
   count nobody counts.
3. `.github/unwired-guards-baseline.txt` needs an edit that its own prose forbids
   being silent about: `src/ai/execution/verify.rs verify_execution_proof_structural`
   is no longer unwired, and `src/core/block.rs verify_signature_with_pubkey` is.
   The count stays 3 either way, but the paragraph under it names the wrong guard.
   The owner of the file should replace that paragraph and lower the number in the
   same change rather than after it.
